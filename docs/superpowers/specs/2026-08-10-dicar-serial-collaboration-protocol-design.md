# DiCar Tune 串口协议与单车多主机协作设计规格

- 状态：设计已确认，待用户复核书面规格
- 日期：2026-08-10
- 协议代号：DCTP
- 协议版本：1
- 适用平台：Windows 首发客户端、后续 macOS/Linux/移动端/Web 客户端
- 适用硬件：车端普通款无线 DAP + 电脑端迷你款无线主机

本文是《DiCar Tune 无线调参与遥测平台设计规格》的专项细化。发生冲突时，本文取代原规格中的串口帧、会话、遥测类型、候选无线 DAP 和多人协作相关描述。

## 1. 已确认的设计决策

1. 一辆车可以绑定多个电脑端迷你主机，但同一时刻只允许一个主机与一个车端普通款通信。
2. 多个主机用于轮流调参和烧录，不提供多条无线链路并发访问同一车辆。
3. 所有团队成员可以查看波形；非活动成员通过活动电脑的数据转发查看，不直接占用无线链路。
4. 新主机不能强制抢占。当前控制者必须批准交接；当前主机断线或连续 3 秒无心跳后，租约自动释放。
5. 调参权限与烧录权限分离。烧录、复位和参数 Flash 固化期间禁止控制权交接。
6. 串口采用 COBS 分帧的二进制协议；不允许在同一 UART 裸输出 `printf`，日志必须封装为协议消息。
7. 参数写入先修改 RAM，用户显式审阅后才固化到 Flash。
8. 编码器的原始 PPR、正交倍频和有效 CPR 必须分开表示；原始计数和计算后的轮速必须同时可观测。
9. 普通调参链路断开不触发车辆停车，也不把 RAM 参数突然恢复为 Flash 值。烧录准备是唯一默认要求车辆安全停机的调试操作。

## 2. 范围与边界

### 2.1 本规格覆盖

- 电脑与车辆 MCU 之间的 UART 应用协议。
- 参数发现、读取、RAM 写入、冲突检测和 Flash 固化。
- 编码器、PID、传感器和状态量的实时遥测。
- 结构化日志、链路诊断、重连和故障恢复。
- 多个主机绑定一辆车时的独占控制租约、权限和波形转发。
- 无线 SWD/JTAG 烧录前后的安全协调流程。
- 参数变更的审计记录和 Git 风格版本模型。

### 2.2 本规格不覆盖

- 无线 DAP 内部射频协议和配对算法。
- MCU 在线调试器协议本身，如 CMSIS-DAP、SWD 和 JTAG 的底层实现。
- 远程驾驶或车辆安全闭环。调试链路断开不能成为车辆失控的单点原因。
- 对绕过 DiCar Tune、直接使用第三方工具连接硬件的恶意客户端进行硬件级阻断。
- 首版的自动 PID 整定或 AI 调参算法。

## 3. 系统拓扑

### 3.1 硬件角色

- **车辆端从机**：普通款无线 DAP，固定安装或连接到车辆，UART 连接 MCU，SWD/JTAG 连接调试口。
- **电脑端主机**：迷你款无线 DAP，每位需要直接接管车辆的成员可配置一个。
- **活动主机**：当前唯一与车辆端从机通信的电脑端主机。
- **候选主机**：已绑定车辆但尚未获得控制租约的其他主机。

首套“普通款 + 迷你款”即可完成一主一从验证。增加参与者时，只增加电脑端主机，不在车上增加多个从机。

### 3.2 软件角色

- **车辆 MCU + DiCar SDK**：解析协议、管理参数和遥测、执行安全准备与持久化。
- **活动桌面客户端**：独占 COM 口，执行协议会话，并作为车辆数据的边缘网关。
- **协作服务**：管理账户、团队、车辆成员、权限、控制租约和审计事件。
- **观察客户端**：通过局域网或云端 WebSocket 接收活动桌面客户端转发的波形和状态快照。

只有活动桌面客户端访问串口。观察客户端和候选主机不能同时打开同一车辆的物理链路。

### 3.3 可信边界

首版的协作锁由 DiCar Tune 客户端和协作服务共同执行。车辆 MCU 只验证 DCTP 会话，不验证云账户身份。该设计适用于可信团队，并保证符合协议的客户端不会并发写入。

如果用户绕过平台直接使用第三方调试工具，软件租约无法绝对阻止连接。后续可以增加车端短期控制令牌，但不作为首版 MCU SDK 的复杂度负担。

## 4. 控制权与权限

### 4.1 权限模型

| 权限 | 能力 |
| --- | --- |
| 观察 | 查看实时波形、状态和已公开日志 |
| 调参 | 申请控制权、修改 RAM 参数、保存参数方案 |
| 烧录/固化 | 把审阅后的参数写入 MCU Flash、安全停机、复位并执行 SWD/JTAG 固件烧录 |
| 车辆所有者 | 管理成员与权限、批准交接、结束异常会话、查看完整审计记录 |

拥有 `调参` 权限不会自动获得 `烧录/固化` 权限。车辆所有者可以把多个权限授予同一成员。

### 4.2 租约状态机

租约状态为：

`离线 → 可申请 → 等待批准 → 已占用 → 调参中/固化中/烧录锁定 → 释放`

规则如下：

1. 新主机申请控制权时，如果车辆空闲，可以直接获得租约。
2. 如果已有控制者，新主机进入等待队列，不能强制抢占。
3. 当前控制者批准后，旧客户端先停止写入、结束 DCTP 会话并释放无线链路；新客户端随后连接并重新握手。
4. 活动客户端每 500 ms 向协作服务和车辆分别发送心跳。
5. 连续 3 秒没有有效心跳时，协作服务把租约标为失效。新主机仍必须重新握手和读取车辆真实状态。
6. `固化中`、`准备烧录` 和 `烧录锁定` 状态禁止交接。
7. 车辆所有者可以结束卡死会话，但不能跳过烧录工具已经进行的物理写入过程；结束动作必须记录审计事件。

### 4.3 波形共享

活动客户端接收完整遥测，将原始记录写入本地，同时以批次形式向协作服务或局域网会话转发。观察者收到只读数据流，不发送车辆协议命令。

活动客户端断线后，波形源随之停止。系统不得伪造“车辆仍在线”，而应冻结最后画面并显示数据源断开时间。

## 5. DCTP 传输层

### 5.1 字节序和分帧

- 多字节整数和浮点数均为小端。
- 浮点数使用 IEEE 754 `float32`。
- 解码后的原始帧经过 COBS 编码，线上以单个 `0x00` 结束。
- 解析器遇到损坏数据时丢弃到下一个 `0x00`，保证有限时间内恢复同步。
- 解码后的 Payload 首版最大为 1024 字节，双方在握手中协商实际最大值。

### 5.2 解码后帧格式

| 字段 | 类型 | 字节 | 说明 |
| --- | --- | ---: | --- |
| Magic | `u16` | 2 | 固定 `0x5444`，小端线上为 ASCII `DT` |
| Version | `u8` | 1 | 首版为 `1` |
| Message Type | `u8` | 1 | 消息类型 |
| Flags | `u8` | 1 | ACK、响应、错误和分片标志 |
| Sequence | `u16` | 2 | 请求匹配、重复检测和诊断 |
| Session ID | `u32` | 4 | 当前物理连接会话；`HELLO` 使用 `0` |
| Payload Length | `u16` | 2 | Payload 实际长度 |
| Payload | bytes | 0–1024 | 消息负载 |
| CRC16 | `u16` | 2 | 覆盖 Magic 至 Payload |

固定头部为 13 字节，不包含 CRC。任何 Length 超过协商上限的帧在分配 Payload 缓冲前拒绝。

### 5.3 Flags

| 位 | 名称 | 含义 |
| ---: | --- | --- |
| 0 | `ACK_REQUIRED` | 请求需要可靠响应 |
| 1 | `RESPONSE` | 当前帧是对请求的响应 |
| 2 | `ERROR` | Payload 是结构化错误 |
| 3 | `MORE_FRAGMENTS` | 同一逻辑消息还有后续分片 |
| 4–7 | Reserved | 首版发送为 0，接收端忽略未知保留位 |

### 5.4 CRC

使用 CRC-16/CCITT-FALSE：

- 多项式：`0x1021`
- 初值：`0xFFFF`
- 输入和输出不反射
- 输出异或：`0x0000`

CRC 错误帧不发送否定 ACK，因为帧头本身可能已损坏；双方只更新诊断计数并依靠请求方超时重试。

### 5.5 波特率

首选波特率为 921600，但只有在目标无线 DAP 通过硬件资格测试后才成为项目默认值。项目必须允许 460800 和 115200 回退。波特率由项目连接配置管理，不在活动会话中自动切换，避免两端不同步。回退速率不承诺维持 8 通道 × 500 Hz；App 必须根据实测有效吞吐降低通道数或采样率，始终为 P0/P1 预留带宽。

## 6. 会话与消息

### 6.1 会话建立

1. 客户端取得协作租约并打开 COM 口。
2. 客户端发送 `HELLO`，其中 `Session ID = 0`，Payload 包含随机 `client_nonce`、支持的协议版本和最大帧长。
3. 设备返回 `HELLO_ACK`，包含非零 Session ID、设备 ID、启动计数、固件版本、SDK 版本、能力位、Manifest 哈希和最大帧长。
4. 设备一旦接受新会话，立即使上一 DCTP Session ID 失效。
5. 客户端获取 Manifest。哈希未变化时允许复用本地描述缓存，但仍必须重新读取全部运行值和固化值。
6. 客户端订阅遥测，完成后进入 `READY`。

Session ID 用于拒绝旧会话残留数据，不作为密码或身份凭据。资源有限的 MCU 可以用 `client_nonce`、启动计数和本地递增会话计数生成 Session ID，无需硬件随机数。

### 6.2 消息类型

| 值 | 消息 | 方向 | 可靠性 |
| ---: | --- | --- | --- |
| `0x01` | `HELLO` | App → MCU | 请求/响应 |
| `0x02` | `HELLO_ACK` | MCU → App | 响应 |
| `0x03` | `HEARTBEAT` | 双向 | 请求/响应 |
| `0x04` | `HEARTBEAT_ACK` | 双向 | 响应 |
| `0x05` | `SESSION_CLOSE` | App → MCU | 请求/响应 |
| `0x10` | `MANIFEST_REQUEST` | App → MCU | 请求/响应 |
| `0x11` | `MANIFEST_CHUNK` | MCU → App | 分片响应 |
| `0x12` | `MANIFEST_DONE` | MCU → App | 响应 |
| `0x20` | `PARAM_READ` | App → MCU | 请求/响应 |
| `0x21` | `PARAM_VALUE` | MCU → App | 响应 |
| `0x22` | `PARAM_WRITE` | App → MCU | 请求/响应 |
| `0x23` | `PARAM_WRITE_ACK` | MCU → App | 响应 |
| `0x24` | `PARAM_COMMIT` | App → MCU | 请求/响应 |
| `0x25` | `PARAM_COMMIT_ACK` | MCU → App | 响应 |
| `0x30` | `TELEMETRY_SUBSCRIBE` | App → MCU | 请求/响应 |
| `0x31` | `TELEMETRY_SUBSCRIBE_ACK` | MCU → App | 响应 |
| `0x32` | `TELEMETRY_DATA` | MCU → App | 不重传 |
| `0x33` | `TELEMETRY_STOP` | App → MCU | 请求/响应 |
| `0x40` | `LOG_MESSAGE` | MCU → App | 不重传 |
| `0x41` | `DEVICE_EVENT` | MCU → App | 不重传，关键事件可要求 ACK |
| `0x50` | `PREPARE_FLASH` | App → MCU | 请求/响应 |
| `0x51` | `PREPARE_FLASH_ACK` | MCU → App | 响应 |
| `0x7F` | `ERROR` | 双向 | 响应或事件 |

### 6.3 Sequence 与幂等

- 请求方为每个新请求分配 Sequence，响应必须回显相同值。
- 重试必须沿用原 Sequence，不能产生第二个逻辑操作。
- MCU 至少缓存当前会话最近 32 个可靠请求的 `(Message Type, Sequence, Result)`；重复请求直接返回缓存结果。
- `PARAM_COMMIT`、`PREPARE_FLASH` 和其他有副作用命令必须幂等。
- 遥测样本使用 Payload 内独立的样本序号统计丢包，不依赖帧 Sequence。

### 6.4 超时

- 普通读写命令：300 ms，最多重试 3 次。
- Manifest 分片：500 ms，最多重试 3 次。
- 参数 Flash 固化：3000 ms，最多重试 2 次，沿用原 Sequence。
- 烧录准备：1000 ms，最多重试 2 次。
- 心跳间隔：500 ms。
- 会话和协作租约失效：连续 3000 ms 无有效帧。

超时只停止 App 继续写入，不改变 MCU 的车辆控制算法和当前 RAM 参数。

## 7. 发送优先级和拥塞控制

MCU 与桌面端都采用有界队列，不允许动态无限增长：

| 优先级 | 数据 | 拥塞策略 |
| --- | --- | --- |
| P0 | 心跳、错误、安全停机、烧录准备 | 不得被低优先级数据阻塞 |
| P1 | 参数读写、固化、Manifest、可靠 ACK | 保留容量，有限重试 |
| P2 | 实时遥测 | 按完整批次丢弃并报告缺口 |
| P3 | 结构化日志 | 最先丢弃，累计丢弃计数 |

发送器在每个低优先级批次之间检查高优先级队列。遥测批次不能大到让 P0/P1 等待超过 20 ms。达到压力阈值时，设备先减少遥测批次数量或采样率，再丢弃完整遥测帧；绝不发送半帧。

## 8. 参数模型

### 8.1 参数描述

每个参数由固件 Manifest 提供：

- 稳定 `param_id: u32`
- 机器名、中文显示名、分组和单位
- 类型：`i32`、`u32`、`f32`、`bool`、`enum`
- 最小值、最大值、步长和默认值
- 标志：只读、可写、可固化、危险操作
- 枚举选项或位标志描述

Manifest 字符串统一使用 UTF-8。机器名最长 48 字节、显示名最长 64 字节、分组最长 32 字节、单位最长 16 字节；解析器在复制前验证长度。机器名在同一设备产品线内保持稳定。显示名可以修改，参数方案和审计记录以 ID 为主、机器名为可读辅助。

### 8.2 运行状态

每个参数具有：

- RAM 运行值
- Flash 固化值
- `value_revision: u32`
- 是否与固化值不同

参数值无论因 DCTP 写入还是固件内部逻辑而变化，设备都递增 `value_revision`。版本回绕按模 `2^32` 处理；一次会话内只判断相等，不比较大小。

### 8.3 PARAM_WRITE

Payload 包含：

1. `param_id`
2. `expected_revision`
3. 类型标签
4. 目标值

设备必须再次检查 Session ID、参数存在性、类型、权限标志、范围和 Revision。成功响应返回设备实际采用的值和新 Revision。Revision 不匹配时返回 `REVISION_CONFLICT`、当前值和当前 Revision，客户端不得静默覆盖。

滑杆连续调整时，每个参数最多保留一个在途写请求；后续中间值在客户端合并，只发送最新目标值。

### 8.4 PARAM_COMMIT

固化请求包含待固化参数 ID 列表、当前 Revision 和整组运行值 CRC32。CRC32 的规范输入为按 `param_id` 升序排列的 `param_id + type + 小端值字节`。设备只有在全部 Revision 与 CRC32 匹配时才写入 Flash。

参考持久化格式采用 A/B 双槽：

- Magic 和存储格式版本
- Manifest CRC32
- 递增 Generation
- Payload Length
- 持久化参数值
- 整体 CRC32

写入非活动槽、校验读回成功后才切换有效 Generation。写入失败时保留上一槽，RAM 值可以继续运行，但 App 必须保持“未固化”状态。

## 9. 编码器参数与遥测

### 9.1 必备编码器参数

| 机器名 | 类型 | 说明 |
| --- | --- | --- |
| `encoder.left.ppr` | `u32` | 左编码器每转原始脉冲数 |
| `encoder.right.ppr` | `u32` | 右编码器每转原始脉冲数 |
| `encoder.quadrature_multiplier` | `enum` | `1`、`2` 或 `4` |
| `encoder.left.cpr` | `u32` 只读 | 左有效计数数，`PPR × 倍频` |
| `encoder.right.cpr` | `u32` 只读 | 右有效计数数，`PPR × 倍频` |
| `encoder.left.inverted` | `bool` | 左方向修正 |
| `encoder.right.inverted` | `bool` | 右方向修正 |
| `drive.wheel_diameter_mm` | `f32` | 轮径 |
| `drive.gear_ratio` | `f32` | 电机轴到车轮的传动比 |
| `encoder.sample_period_us` | `u32` | 速度计算采样周期 |
| `encoder.speed_lpf_hz` | `f32` | 速度低通滤波截止频率 |
| `encoder.jump_threshold_counts` | `u32` | 单周期异常跳变阈值 |
| `encoder.max_credible_rpm` | `f32` | 最大可信转速 |
| `encoder.missing_pulse_detection` | `bool` | 丢脉冲诊断开关 |

App 必须分别显示 PPR、倍频和 CPR，不使用含糊的“编码器线数”单字段。

### 9.2 默认编码器遥测

- 左右单周期计数增量 `i32`
- 左右累计计数 `u32`，允许自然回绕，App 展开为 64 位
- 左右轮速 `f32`
- 估算车速 `f32`
- 左右轮差速 `f32`
- 目标速度和速度误差 `f32`
- 异常跳变计数 `u32`
- 溢出、丢脉冲、方向异常等 `u32 flags`
- 采样周期抖动 `u32`
- 左右电机 PWM 或归一化输出 `f32`

## 10. 遥测协议

### 10.1 通道 Manifest

每个通道包含稳定 ID、机器名、显示名、分组、单位和 32 位标量类型。首版支持 `f32`、`i32`、`u32` 和 `flags32`，每个样本中的通道值统一占 4 字节。

首版同时订阅最多 8 个通道，每通道目标最高 500 Hz。固件可以注册至少 16 个候选通道，用户从中选择 8 个显示和记录。

### 10.2 TELEMETRY_DATA Payload

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| Subscription Version | `u16` | 防止旧订阅数据混入新布局 |
| First Sample Sequence | `u16` | 批次首样本序号 |
| Sample Count | `u8` | `1–16` |
| Channel Count | `u8` | 首版 `1–8` |
| Dropped Samples | `u16` | 自上一帧起设备主动丢弃的样本数 |
| Base Timestamp | `u32` | 设备单调微秒时钟 |
| Samples | bytes | 每个样本为 `dt_us: u16` + N 个 32 位值 |

首个样本 `dt_us = 0`，后续值表示相对前一样本的微秒差。批次最多 16 个样本，但最长 16 ms 必须发送一次，以控制观察延迟。设备时间戳发生 `u32` 回绕时由 App 展开。

遥测不重传。记录器保留完整批次；绘图层独立降采样，不能为了画图性能修改原始记录。

## 11. 日志

车端禁止在 DCTP UART 裸输出文本。`LOG_MESSAGE` 包含：

- 设备时间戳
- 严重级别：Trace、Debug、Info、Warn、Error
- 模块 ID
- UTF-8 文本，首版最长 192 字节

日志属于 P3。队列拥塞时允许丢弃，并在后续诊断状态中报告累计丢弃数量。Error 级日志可以额外产生 P0/P1 的结构化 `DEVICE_EVENT`，但长文本仍不提高优先级。

## 12. 错误模型与恢复

### 12.1 错误码

首版至少定义：

- `UNSUPPORTED_VERSION`
- `INVALID_SESSION`
- `UNKNOWN_MESSAGE`
- `INVALID_LENGTH`
- `INVALID_PARAM_ID`
- `TYPE_MISMATCH`
- `OUT_OF_RANGE`
- `READ_ONLY`
- `REVISION_CONFLICT`
- `BUSY`
- `QUEUE_FULL`
- `STORAGE_FAILED`
- `VERIFY_FAILED`
- `NOT_READY`
- `INTERNAL_ERROR`

错误响应必须包含原请求 Message Type、Sequence、错误码和可选的机器可读上下文；中文提示由 App 映射，设备不承担 UI 文案。

### 12.2 断线

- App 立即停止新写命令，冻结波形并显示断开时间。
- 车辆继续使用最后接受的 RAM 参数运行。
- 未固化项在 App 中标为“设备状态未知”，不能误报为已保存或已丢失。
- 新连接建立新 Session，重新读取真实值；不能自动重放旧缓存写入。
- MCU 复位后从最新有效 Flash 槽加载参数，因此未固化 RAM 值自然消失。

### 12.3 Manifest 变化

固件更新后如果 Manifest CRC32 变化，App 重新下载完整 Manifest。旧参数方案按稳定 ID 匹配，并明确列出缺失、类型变化和越界项目；这些项目不得自动应用。

### 12.4 重复命令

同一 Session 中重复的可靠命令返回缓存结果。旧 Session 的命令返回 `INVALID_SESSION`。客户端收到该错误后必须停止重试并重新握手。

## 13. 无线烧录协调

实际固件传输由无线 DAP 的 CMSIS-DAP/SWD/JTAG 能力完成，不封装进 DCTP UART Payload。DCTP 只负责安全协调：

1. 用户必须拥有烧录权限并取得控制租约。
2. 协作服务把会话切换到 `烧录锁定`，冻结交接。
3. App 发送 `PREPARE_FLASH`，包含计划烧录的固件标识。
4. MCU 按项目回调执行电机安全停机、关闭高功率输出、暂停遥测，并返回 `PREPARE_FLASH_ACK`。
5. App 关闭或暂停串口会话，调用经过验证的烧录工具链。
6. 烧录完成后重新枚举设备、建立新 DCTP Session、读取固件版本和 Manifest。
7. 只有固件校验和重新握手均成功，才解除烧录锁定。

烧录失败或工具异常退出时保持锁定和安全停机提示，直到操作者明确重试或结束恢复流程。平台记录固件 SHA-256、可选 Git commit、操作者、车辆、开始/结束时间和工具输出摘要。

## 14. 参数版本控制

平台采用 Git 风格模型，但不把每次滑杆移动直接映射为 Git commit：

- **工作区**：当前 RAM 参数与固化值之间的差异。
- **变更集**：用户审阅后形成的一组参数修改，包含旧值、新值、参数 Revision、车辆、固件和 Manifest 标识。
- **参数快照**：带说明、作者和时间的可恢复版本。
- **固化记录**：设备确认写入 Flash 后产生，关联参数快照和设备 Generation。
- **Git 关联**：参数快照可以导出到项目仓库，并关联源码 commit；平台也可以通过 Git 集成提交可读 JSON，但此动作由用户显式触发。

观察者只能读取版本记录；调参者可以创建工作区和参数快照；固化仍要求 `烧录/固化` 权限。

## 15. 性能目标

在候选无线 DAP 通过资格测试后：

- 8 通道 × 500 Hz 的 32 位遥测持续运行 30 分钟，序号缺口率低于 0.5%。
- 活动桌面端参数写入到设备 ACK 的第 95 百分位不超过 100 ms。
- 同一局域网观察端的波形端到端第 95 百分位延迟不超过 250 ms。
- 云端观察延迟作为网络质量指标展示，首版目标为第 95 百分位不超过 500 ms，不承诺远程实时控制。
- P3 日志洪泛不能导致心跳超时或 P1 参数命令等待超过 300 ms。
- 车端 SDK 在注册 64 个参数和 16 个遥测通道时，额外资源目标仍为不超过 16 KiB Flash 和 4 KiB RAM，最终以构建产物为准。

## 16. 测试与验收

### 16.1 协议自动化测试

- COBS、CRC、最大长度和各字段的黄金向量。
- 随机噪声、截断、重复分隔符、错误 Length 和 CRC 的解析器模糊测试。
- Sequence 回绕、重复命令、32 项结果缓存和旧 Session 拒绝。
- 所有参数类型、范围边界、Revision 冲突、连续滑动合并和 Flash 幂等。
- 混合 `f32/i32/u32/flags32` 遥测、时间戳回绕、批次缺失和订阅切换。
- 日志洪泛、遥测拥塞和 P0/P1 优先级保证。
- A/B 双槽写入成功、写失败、读回失败和掉电故障注入。

### 16.2 硬件测试

1. 使用一套普通款 + 迷你款完成串口调参、遥测和 SWD/JTAG 烧录。
2. 至少三个电脑端主机绑定同一车辆，连续执行 100 次控制权交接。
3. 验证旧主机没有释放时新主机不能接管；断开旧主机后 3 秒超时可以接管。
4. 每次接管都产生新 Session，并重新读回参数；旧写请求不能生效。
5. 在 921600、460800 和 115200 下分别测量有效吞吐、CRC 错误和重连。
6. 8 × 500 Hz 遥测连续 30 分钟，验证序号缺口和 UI 延迟。
7. 车端断电、电脑端拔插、无线超距和 MCU 复位后均能明确恢复。
8. 在烧录过程中尝试申请交接，系统必须拒绝；烧录失败后保持安全恢复状态。
9. STM32 与 TI MSPM0 各完成一次编码器参数标定、RAM 调参、Flash 固化和复位读回。

### 16.3 协作验收

- 所有成员可以同时查看活动主机转发的同一波形时间线。
- 没有调参权限的成员不能发送参数写入。
- 有调参但无烧录权限的成员不能固化、复位或烧录。
- 控制交接、参数变更、固化和烧录均生成不可静默删除的审计事件。
- 活动主机断开时，观察者界面冻结并显示断开时间，不继续滚动伪造数据。

## 17. 分阶段实现

1. **协议基线**：帧编解码、模拟设备、会话、Manifest、参数 RAM 写入和混合类型遥测。
2. **车端闭环**：STM32/MSPM0 SDK、编码器参数、A/B 持久化、日志和异常恢复。
3. **硬件资格与本地产品**：普通款 + 迷你款实测、Windows App、记录回放和参数版本。
4. **协作扩展**：团队权限、控制租约、活动主机波形转发、审计和多主机交接。
5. **无线烧录扩展**：安全准备、工具链封装、固件记录和烧录锁定。
6. **跨平台与智能扩展**：macOS、Linux、移动端、Web Serial、AI 调参和多车辆并行会话。

阶段 4–6 可以在首版核心开发期间并行启动，但按依赖关系分批发布。任何扩展客户端都复用同一 DCTP Schema 和协议测试向量，不能各自定义不兼容的串口格式。

## 18. 实施前必须锁定的外部事实

以下不是设计空缺，而是硬件资格测试输入：

1. 迷你主机与普通车端从机的地址配置格式和可配置数量上限。
2. 多主一从切换是否需要手动按键、重新上电或等待射频超时。
3. UART 无线透传在各波特率下的真实吞吐和双工行为。
4. SWD/JTAG 烧录与 UART 是否可以同时保持，还是必须释放串口。
5. Windows 下虚拟 COM 和 CMSIS-DAP 设备标识是否稳定，可否可靠映射到同一物理主机。

资格测试结果只决定连接适配器和默认配置，不改变 DCTP 帧和车辆 SDK 的核心设计。
