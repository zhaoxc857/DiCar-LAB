# DiCar Tune 无线调参与遥测平台设计规格

> 专项更新：串口帧、会话、混合类型遥测、单车多主机协作和无线烧录协调，以 [DiCar Tune 串口协议与单车多主机协作设计规格](./2026-08-10-dicar-serial-collaboration-protocol-design.md) 为准。

- 状态：设计已确认，待用户复核书面规格
- 日期：2026-08-10
- 首版平台：Windows 桌面端
- 首批用户：团队内部，面向 STM32 与 TI MSPM0 项目

## 1. 产品目标

DiCar Tune 用于电子设计竞赛和智能车竞赛的现场调试。它通过标准串口与无线透传硬件通信，让用户无需反复修改常量、重新编译和烧录，即可在车辆运行时调整参数、观察波形、记录数据，并在确认效果后把参数显式固化到 MCU Flash。

首版成功标准：

1. Windows 电脑通过候选无线 DAP 的标准 COM 口连接 STM32 或 MSPM0 目标板。
2. 固件自动上报参数与遥测通道元数据，App 不维护重复的参数清单。
3. 用户可实时调整 RAM 参数，端到端反馈延迟的第 95 百分位不超过 100 ms。
4. 稳定显示并记录 8 个 `float32` 通道、每通道 500 Hz 的遥测数据。
5. 用户显式审阅后才可固化参数；复位后读回值与固化结果一致。
6. 断线、CRC 错误、设备复位或写 Flash 失败时，不静默丢失状态或误报成功。

### 1.1 首版范围

- Windows 离线桌面 App。
- 标准 COM 串口连接，不绑定某一款无线硬件的专有协议。
- 参数发现、读写、搜索、分组、收藏、修改追踪与显式固化。
- 实时波形、基础游标、会话记录、回放和 CSV 导出。
- 参数集保存、比较、导入和应用。
- 链路诊断：延迟、吞吐、CRC 错误、序号缺口和重连状态。
- STM32 与 TI MSPM0 的纯 C 车端 SDK 示例与移植层。

### 1.2 非首版范围

- SWD/JTAG 无线烧录、断点调试和 Bootloader 更新。
- 手机、平板、macOS、Linux 和纯 Web Serial 客户端。
- 云账户、团队协作、远程控制或公开插件市场。
- 自动 PID 整定和基于 AI 的调参建议。
- 同时连接多辆车。

## 2. 用户体验与信息架构

### 2.1 菜单主页

主页采用卡片式菜单，承担功能导航而不是实时操作。顶部始终显示当前项目、设备、COM 口、波特率和连接状态。

首版功能入口：

- **实时调参与波形**：进入主要工作台。
- **数据记录与回放**：打开历史会话、游标测量和 CSV 导出。
- **参数方案库**：保存、比较、导入与应用整车参数集。
- **连接与链路诊断**：选择端口、查看握手信息、吞吐、延迟和错误统计。

主页同时显示当前项目摘要，包括固件版本、参数数量、可选遥测通道数和最后固化时间。

### 2.2 实时调参工作台

工作台采用固定三栏结构：

1. **左栏：参数导航**
   - 搜索、收藏、仅看已修改、最近调整。
   - 参数分组、数量和未固化标记。
   - 本地参数集快捷入口。
2. **中栏：参数编辑**
   - 根据类型自动选择滑杆、数字框、开关或枚举控件。
   - 同时显示设备固化值和当前 RAM 运行值。
   - 修改立即写入 RAM；失败时恢复界面值并显示原因。
3. **右栏：实时波形**
   - 默认最多显示 8 个通道，允许从固件上报的通道中替换。
   - 支持暂停、时间窗口、游标、通道显隐和基础统计。
   - 固定显示采样率、延迟、丢包率和记录状态。

底部使用统一的变更栏汇总所有未固化项，提供撤销全部、保存参数集和“审阅并固化”操作。固化前必须展示参数名、固化前值和运行值；关闭窗口、切换项目或断开连接时，若存在未固化变化，必须明确提示。

首版不提供卡片拖拽和自由布局编辑器，以降低误操作和布局维护成本。

### 2.3 参数分组

固件负责上报分组，App 只提供一致的渲染规则。示例项目至少覆盖：

| 分组 | 典型参数 |
| --- | --- |
| 速度控制 | 目标速度、加速度限制、Kp/Ki/Kd、积分上限、输出限幅、反馈滤波 |
| 转向控制 | 中值、Kp/Kd、前馈、舵机上下限、弯道增益、输出平滑 |
| 电机与输出 | 左右 PWM 死区、最大输出、加减速斜率、左右轮补偿、电流限制 |
| 编码器与里程计 | 左右 PPR、正交倍频、轮径、传动比、方向修正、采样周期、滤波和异常阈值 |
| 其他传感器标定 | 电感/灰度/摄像头偏置与增益、IMU 零偏、滤波截止频率和阈值 |
| 赛道策略 | 直道/弯道速度、环岛模式、坡道策略、障碍使能和策略枚举 |
| 安全与保护 | 失线超时、低压阈值、过流阈值、最大可信速度和故障降级开关 |

编码器分组必须区分原始 PPR 与正交倍频后的有效 CPR，避免把线数和计数数混用。默认提供左轮转速、右轮转速、估算车速、左右轮差速、原始计数增量、异常跳变和丢脉冲状态等遥测通道。

### 2.4 视觉与交互约束

- 中文优先的深色高密度界面，目标分辨率 1280×720 及以上。
- 状态不能只依赖颜色，必须同时使用文本或图标。
- 危险操作与普通操作分色；写 Flash 使用独立的审阅确认流程。
- 常用操作支持键盘：全局搜索、连接/断开、暂停波形、添加标记和撤销最近修改。
- 实时数值最多按 30 Hz 刷新界面，后台采样仍保持 500 Hz；波形使用 Canvas 渲染和按像素降采样，避免 UI 重绘影响通信。

## 3. 系统架构

### 3.1 桌面端

桌面端采用 Tauri 2：React + TypeScript 构建界面，Rust 后端负责所有硬件 I/O 与高频数据处理。

Rust 后端拆分为：

- **Serial Manager**：端口枚举、打开、关闭、波特率、重连和端口身份记录。
- **Protocol Session**：帧编码/解码、握手、序号、请求超时、ACK、心跳和能力协商。
- **Parameter Service**：参数清单、运行值、固化值、待提交变更和参数集转换。
- **Telemetry Engine**：订阅管理、时间戳展开、环形缓冲、降采样和 UI 批量推送。
- **Recorder/Replay**：追加式会话记录、回放时钟和 CSV 导出。
- **Diagnostics**：吞吐、往返延迟、CRC 错误、序号缺口、缓冲区压力和重连原因。

前端不直接访问串口。它通过窄接口向 Rust 发命令，并接收批量状态快照；高频遥测不会逐样本跨越 Tauri 边界，而是由 Rust 每 16–33 ms 批量推送。

### 3.2 车端 SDK

车端 SDK 使用 C11 可兼容子集，不依赖操作系统和动态内存。核心只依赖三个移植接口：

- UART 非阻塞收发。
- 单调递增微秒时钟。
- 可选的参数持久化读写与校验回调。

建议公开接口：

```c
dctune_status_t dctune_init(
    const dctune_transport_t *transport,
    const dctune_clock_t *clock,
    const dctune_storage_t *storage);

void dctune_poll(void);

dctune_status_t dctune_register_param(const dctune_param_desc_t *desc);
dctune_status_t dctune_register_telemetry(const dctune_telem_desc_t *desc);
```

便捷宏如 `DCT_PARAM_F32`、`DCT_PARAM_BOOL` 和 `DCT_TELEM_F32` 只包装显式注册调用，不依赖编译器链接段魔法，从而兼容 GCC、Keil、IAR 和 TI 工具链。

目标资源预算：注册 64 个参数和 16 个遥测通道时，核心额外占用不超过 16 KiB Flash、4 KiB RAM；最终以构建产物测量值为准。

## 4. 串口协议

### 4.1 帧格式

首版使用二进制、小端、版本化协议。原始帧经 COBS 编码并以 `0x00` 分隔，解码后的结构为：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| Magic | `u16` | 固定为 `0x5444`，线上字节为 ASCII `DT` |
| Version | `u8` | 首版固定为 `1` |
| Message Type | `u8` | 消息类型 |
| Flags | `u8` | ACK、错误和分片标记 |
| Sequence | `u16` | 命令匹配与丢帧检测 |
| Payload Length | `u16` | 负载字节数 |
| Payload | bytes | 类型对应数据 |
| CRC16 | `u16` | CRC-16/CCITT-FALSE，覆盖头部和负载 |

CRC 参数固定为多项式 `0x1021`、初值 `0xFFFF`、不反射、输出异或 `0x0000`。损坏帧直接丢弃并计入诊断；解析器必须在任意字节流位置通过下一个 `0x00` 恢复同步。

### 4.2 握手与消息

连接流程：

1. App 打开用户选择的 COM 口，默认尝试项目保存的波特率；新项目默认 921600，可手动降至 460800 或 115200。
2. App 发送 `HELLO`，设备返回协议版本、设备 ID、固件版本、SDK 版本、能力位和最大帧长度。
3. App 请求参数与遥测 Manifest；Manifest 支持分片并带整体哈希。
4. App 读取全部当前值和固化值，再开放编辑与订阅功能。
5. 双方以 500 ms 心跳维持会话；连续 1500 ms 无有效响应则进入断线状态。

首版消息类型：

- `HELLO` / `HELLO_ACK`
- `MANIFEST_REQUEST` / `MANIFEST_CHUNK`
- `PARAM_READ` / `PARAM_VALUE`
- `PARAM_WRITE` / `PARAM_WRITE_ACK`
- `PARAM_COMMIT` / `PARAM_COMMIT_ACK`
- `TELEMETRY_SUBSCRIBE` / `TELEMETRY_DATA`
- `HEARTBEAT` / `HEARTBEAT_ACK`
- `ERROR`

命令必须 ACK 并带序号；普通命令 300 ms 未响应即重试，最多 3 次。重试沿用原序号，设备缓存最近命令结果，保证重复的 `PARAM_COMMIT` 不会再次写 Flash。遥测数据不重传，依靠序号缺口统计丢包。任何协议版本不兼容都要阻止写参数，但允许显示明确的升级提示。

### 4.3 参数模型

每个参数包含：稳定的数值 ID、机器名、显示名、分组、类型、最小值、最大值、步长、单位、默认值、权限和持久化标记。

首版类型：`i32`、`u32`、`f32`、`bool` 和 `enum`。不支持任意字符串、数组和结构体参数。

参数写入规则：

- App 在本地先验证类型与范围，设备必须再次验证。
- `PARAM_WRITE` 只改 RAM；ACK 返回设备最终采用的值。
- 同一参数仅允许一个未完成写请求；连续滑动时 App 合并中间值，避免堆积。
- `PARAM_COMMIT` 携带待固化参数列表及运行值哈希；设备完成持久化、校验读回后才返回成功。
- Flash 写入失败或读回不一致时，运行值仍可保留，但 App 必须保持“未固化”状态并显示错误。
- SDK 将持久化参数序列化为带 Manifest 哈希、递增代数和 CRC32 的记录；STM32 与 MSPM0 参考适配器使用 A/B 双槽写入，启动时选择代数最新的有效槽，掉电不得破坏上一份有效记录。

### 4.4 遥测模型

遥测通道 Manifest 包含稳定 ID、名称、分组、类型和单位。首版实时订阅最多 8 个 `f32` 通道，每通道最高 500 Hz。

一个遥测帧携带设备单调时钟 `timestamp_us`、订阅版本和当前通道值。App 负责展开 32 位时间戳回绕，并使用有界环形缓冲保存最近窗口。记录器接收完整数据；绘图层根据像素宽度降采样，不丢弃记录文件中的原始样本。

## 5. 本地数据

- **项目配置**：JSON，保存端口偏好、波特率、设备 ID、界面偏好和参数集引用。
- **参数集**：可读 JSON，包含设备/Manifest 标识、参数 ID、名称、类型和值。应用前必须展示缺失、类型变化和越界项。
- **会话记录**：`.dctlog` 追加式二进制文件，头部包含 JSON 元数据，随后保存带长度的原始遥测批次和事件标记。
- **CSV 导出**：由记录文件离线生成，不在实时串口线程中写 CSV。

所有数据默认保存在用户本地应用数据目录。首版不上传云端。

## 6. 异常与恢复

- **断线**：立即停止写命令、冻结波形并保留可见数据；未固化项标记为“设备状态未知”。重新握手和读回后再决定是否仍为未固化。
- **设备复位**：通过新会话 ID 识别，重新获取 Manifest；若 Manifest 哈希未变可复用 UI，仍需重新读值。
- **串口拥塞**：优先发送控制命令和心跳，降低遥测订阅率；不允许无限增长队列。
- **CRC/序号错误**：更新诊断统计；命令按有限次数重试，遥测不重传。
- **Manifest 变化**：参数集按稳定 ID 匹配，名称仅用于提示；类型不一致项禁止自动应用。
- **Flash 风险**：只有显式 `COMMIT` 才调用存储回调；滑杆调整不会触发 Flash 写入。

## 7. 候选无线 DAP 验证门槛

软件只依赖标准 COM 透传，因此候选硬件必须在采购锁定前通过：

1. 无线模式在 Windows 稳定枚举虚拟 COM 口，且端口身份可重复识别。
2. 在 921600 波特率下持续 30 分钟全双工传输，应用有效吞吐不低于 30 KiB/s。
3. 8 通道 × 500 Hz 负载下，30 分钟序号缺口率低于 0.5%，无不可恢复解析失步。
4. 车端断电重启后 5 秒内可重新握手；接收器拔插后 App 能明确提示并恢复。
5. 3.3 V UART 电平与目标板兼容，共地和供电方式明确。
6. 分别在一块 STM32 板和一块 MSPM0 板上完成相同测试。

无线 SWD/JTAG 烧录能力不作为首版通过条件。若候选 DAP 未通过串口验证，可替换为任何标准 COM 透传硬件而不改 App 协议和车端 SDK。

## 8. 测试与验收

### 8.1 自动化测试

- 帧编解码黄金向量：边界长度、COBS 特殊字节、CRC、序号回绕。
- 解析器模糊测试：随机截断、噪声、重复分隔符和损坏长度字段。
- 参数测试：所有类型、范围边界、连续滑动合并、超时、拒绝和 ACK 回值。
- 持久化测试：成功、写失败、校验失败、掉电后读回和 Flash 回调缺失。
- 遥测测试：8×500 Hz、时间戳回绕、序号缺口、缓冲区压力和绘图降采样。
- 参数集兼容：缺失 ID、类型变化、越界值、不同 Manifest 哈希。
- UI 测试：连接、搜索、修改、撤销、审阅固化、断线提示、记录与回放。

### 8.2 集成与硬件测试

- Rust 协议层与模拟固件进行环回和故障注入测试。
- STM32 与 MSPM0 示例工程分别验证注册、上报、写 RAM 和 Flash 固化。
- 候选无线 DAP 执行第 7 节的吞吐、稳定性与重连测试。
- 完整 App 在 8×500 Hz 下连续运行 60 分钟，无未受控内存增长、界面卡死或串口线程阻塞。
- 在静止台架、车轮悬空和实际赛道三阶段验证编码器方向、PPR/CPR、速度换算与丢脉冲诊断。

### 8.3 首版验收场景

1. 新项目选择 COM 口并在 5 秒内完成握手，2 秒内呈现 Manifest 和当前值。
2. 调整速度 Kp 后车辆立即采用新值，界面同时显示固化值与运行值。
3. 断电前未固化的值不会被误报为已保存；显式固化的值在复位后正确读回。
4. 同屏查看目标速度、左右编码器速度、速度误差和 PWM，记录后可原速回放并导出 CSV。
5. 断开无线链路后 App 不再发送写命令，恢复连接后重新确认设备真实状态。

## 9. 分阶段交付

1. **通信底座**：协议、Rust 会话层、模拟固件、STM32/MSPM0 SDK 骨架。
2. **参数闭环**：Manifest、类型化控件、RAM 写入、未固化状态和 Flash 提交。
3. **遥测闭环**：8×500 Hz、波形、编码器诊断、记录与回放。
4. **产品化收口**：主页、参数集、链路诊断、安装包和硬件资格测试。

首版先服务团队内部；完成至少两周赛训使用并收集失败日志后，再决定是否扩展无线烧录和公开发布。
