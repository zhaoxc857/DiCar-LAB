# DiCar Tune 透明串口硬件兼容设计规格

- 状态：已确认
- 日期：2026-08-11
- 首批硬件：MuseLab nanoUART-wl、HC-05、通用 COM 串口设备
- 首发平台：Windows 桌面 App

## 1. 目标

在不修改 DCTP v1 线协议的前提下，让 DiCar Tune 通过统一的 Windows COM 传输兼容多种透明串口硬件。首批正式支持：

1. MuseLab nanoUART-wl 电脑端与设备端套装。
2. Windows 蓝牙直接配对车端 HC-05 后产生的 Bluetooth SPP 虚拟 COM 口。
3. 其他能够提供标准 COM 口的有线 USB-TTL 或无线透明传输模块。

只有完成 COM 打开、DCTP HELLO、Manifest 和参数读取后，车辆才进入 `READY`。蓝牙已配对、COM 已出现或串口已打开都不能单独显示为车辆已连接。

## 2. 已确认的硬件事实

### 2.1 nanoUART-wl

MuseLab 官方资料说明 nanoUART-wl 是电脑端与设备端组成的双向无线透明串口，电脑端产生虚拟串口，最高支持 460800 baud。车端通常连接 GND、TX、RX，供电和 IO 按 3.3 V 使用。

来源：<https://github.com/wuxx/nanoUART-wl>

### 2.2 HC-05

HC-05 是 Bluetooth Classic SPP 到 UART 的透明传输模块。采用以下拓扑：

```text
DiCar Tune -> Windows 蓝牙 SPP 虚拟 COM -> HC-05 -> 车辆 MCU UART -> DCTP
```

首版使用一块 HC-05 作为车端从机；第二块可作为备用或另一辆车的车端模块，但不参与同一辆车的并发连接。HC-05 数据串口支持多档可配置波特率；实际 MCU UART 波特率必须与模块的数据模式配置一致。

裸模块 IO 按 3.3 V 逻辑处理。即使某些带底板产品允许 5 V VCC，也不能据此假设 RX 引脚耐受 5 V；5 V MCU 发往 HC-05 RX 时必须使用分压或电平转换。

参考资料：<https://www.dbuelectronics.cr/img/cms/PDF/Bluetooth%20HC-05.pdf>

## 3. 方案选择

评估三种实现方式：

1. **硬件配置档叠加现有 SerialTransport（采用）**：继续使用 Windows COM 与现有 DCTP，会话代码不感知无线硬件型号。
2. 原生 Windows RFCOMM：绕过 COM，但会增加平台专用代码，且对当前目标没有额外收益。
3. 在主 App 内管理 HC-05 AT 模式：需要 KEY/EN 和物理接线，通常不能从已经建立的数据模式蓝牙链路完成，留给以后独立的硬件配置工具。

采用方案 1。它同时覆盖 nanoUART-wl、HC-05 和通用透明串口模块，并保持跨平台 Transport 边界。

## 4. 核心模型

新增 `HardwareProfile`，只描述传输能力和 UI 指引，不改变 DCTP Payload：

- `NanoUartWl`
- `Hc05BluetoothSpp`
- `GenericSerial`

每个配置档包含：

- 用户可见名称与接线说明。
- 推荐波特率和允许探测的波特率列表。
- 默认遥测预算。
- Windows 端点识别提示。
- 配对或链路建立提示。
- 电平安全提示。

串口端点继续使用 `{ portName, baudRate }`。配置档属于连接意图，不能替代真实 `TransportIdentity`；连接成功后的设备身份仍来自已打开的 COM 端点和 DCTP 握手结果。

## 5. 波特率与自动探测

### 5.1 预设

| 配置档 | 推荐起始值 | 可探测值 |
| --- | ---: | --- |
| nanoUART-wl | 460800 | 460800、230400、115200 |
| HC-05 Bluetooth SPP | 115200 | 115200、9600、38400、57600、230400、460800 |
| 通用串口 | 115200 | 由用户显式选择，允许上述值及 921600 |

Windows 蓝牙驱动可能忽略虚拟 COM 的波特率设置，但车端 HC-05 与 MCU 的 UART 配置仍必须一致，因此 UI 仍显示和保存该值。

### 5.2 探测规则

自动探测仅在用户明确点击连接后执行：

1. 按配置档顺序逐个打开同一 COM。
2. 每次只发送 DCTP HELLO，不发送参数写入或固化。
3. 收到有效 HELLO_ACK 后立即锁定当前配置并继续 Manifest。
4. 失败时关闭端口，再尝试下一档；任一时刻只有一个打开的句柄。
5. 所有档位失败时保持断开，并显示已尝试的端口、档位和最后错误。

自动探测不得把随机串口文本、HC-05 AT 响应或打开端口成功当成 DCTP 设备。

## 6. Windows 连接体验

真实串口连接区增加硬件选择：`nanoUART-wl`、`HC-05 蓝牙串口`、`通用串口`。

HC-05 引导固定为：

1. 在 Windows 设置中完成 HC-05 配对。
2. 选择系统创建的“传出/Outgoing”蓝牙 COM 口。
3. 确认车端 MCU 与 HC-05 TX/RX 交叉连接、共地且逻辑电平安全。
4. 选择已知波特率，或使用自动探测。
5. 只有 DCTP 握手成功后进入工作台。

端口发现若能识别 `BluetoothPort`，在 UI 中增加“蓝牙”标记；系统无法提供类型时仍允许手工选择，不能靠端口名称猜测并自动连接。若 Windows 同时创建传入和传出端口，App 不静默替用户选择。

连接状态依次显示：

- 未配对或未发现端口。
- COM 可选。
- 正在打开串口。
- 正在进行 DCTP 握手。
- 正在加载设备定义。
- 已连接。
- 连接失败或链路中断。

## 7. 链路能力与遥测降级

参数读写、心跳和错误响应永远高于遥测。硬件配置档只给出初始预算，运行时根据实际吞吐、重试、CRC 错误和样本缺口继续降低遥测负载。

- nanoUART-wl 默认 460800，可从 8 路较高采样率开始，但仍受真实链路诊断约束。
- HC-05 默认 4 路 × 50 Hz；不得承诺 8 路 × 500 Hz。
- HC-05 在 9600 baud 时默认降为 2 路 × 10 Hz。
- 用户提高通道数或频率时，UI 先显示估算带宽；超出安全预算则拒绝或提供一键降低建议。
- 连续出现积压或样本缺口时，先降低遥测频率，再减少通道；不能牺牲 PARAM_WRITE、PARAM_COMMIT、ERROR 和 HEARTBEAT。

应用保存每个“硬件配置档 + COM 端点”的最后一次成功设置，但断线重连后绝不自动重放未确认的参数写入。

## 8. 诊断与错误处理

诊断页增加：

- 硬件配置档、COM、标称波特率和 DCTP 会话状态。
- 当前接收/发送吞吐。
- CRC/COBS 错误、重试、超时、遥测序号缺口和本地丢弃数。
- 当前遥测预算及降级原因。
- 最近一次成功握手的设置。

稳定错误文案示例：

- “已找到蓝牙串口，但未收到 DiCar DCTP 握手响应。”
- “所选端口可能是传入端口，请选择 Windows 创建的传出 COM 口。”
- “串口可打开，但车端波特率或 DCTP 固件不匹配。”
- “HC-05 链路带宽不足，遥测已从 4×50 Hz 降至 2×25 Hz。”

发生断线时立即停止新写入、把未确认状态标为 Unknown、冻结波形并保留诊断。重新连接必须建立新 Session，并重新读取 Manifest 与参数状态。

## 9. 测试与验收

Rust 测试：

- 三种配置档的波特率顺序和预算。
- 自动探测只发送 HELLO，失败后关闭端口，成功后停止继续探测。
- BluetoothPort 元数据映射和未知类型回退。
- 串口打开成功但无 HELLO_ACK 时不进入 READY。
- 降级策略不丢控制消息，且队列保持有界。
- 断线后不重放旧参数写入。

React/Vitest 测试：

- 三个硬件配置档、HC-05 配对/接线提示和电平警告。
- 蓝牙端口标记、手动选择和自动波特率探测进度。
- COM 打开、DCTP 握手和 READY 状态不混淆。
- 不同波特率下的通道/采样率预算与中文降级原因。

Windows 实机验收：

1. nanoUART-wl 在 460800 baud 完成连接、参数读取、一次 RAM 写入和至少 4 路波形。
2. Windows 与车端 HC-05 配对后，通过传出 COM 完成相同闭环。
3. HC-05 断电后 App 在限定时间内进入断线状态，重新上电连接不重放旧写入。
4. 选择传入 COM、错误波特率或无 DCTP 固件的串口时不误报成功。

## 10. 本阶段边界

本阶段不实现：

- HC-05 AT 模式配置和固件升级。
- iOS 对 Bluetooth Classic SPP 的支持。
- 浏览器直接访问 Web Bluetooth；纯 Web 仅在浏览器和操作系统实际暴露串口时尝试 Web Serial。
- 两台电脑同时连接一块 HC-05。
- 多车并行会话、远程中继和无线 SWD/JTAG 烧录。

这些能力继续复用同一 DCTP 与 Transport 边界，分别进入后续版本。
